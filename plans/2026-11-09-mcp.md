# Plan: Adeli Chat MCP server (`chat.tryadeli.com/mcp`)

> Status: built 2026-11-09. Open item: verify the claude.ai connector on the deployed domain.

Goal: let Claude (claude.ai, Claude Desktop, Claude Code) and other MCP clients list, create and manage a user's Comment to DM automations. Also two sidebar fixes.

Three parts, shipped as three PRs:

1. **Sidebar:** Settings above Automations, and the automation list scrolls on its own.
2. **MCP server + API tokens:** `/mcp` endpoint, automation tools, personal tokens. Works with Claude Code, Cursor and any client that sends a header.
3. **OAuth + Claude preset link:** what claude.ai and Claude Desktop connectors need. This is what makes the one-click "Install in Claude" button work.

---

## How hard is the Claude preset link?

The link itself is one line. Twenty builds it like this (`twentyhq/twenty`, `settings/mcp/utils/mcpSetup.ts`):

```
https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=Adeli%20Chat&connectorUrl=https%3A%2F%2Fchat.tryadeli.com%2Fmcp
```

The catch: a claude.ai custom connector **can't send a static `Authorization` header**. It connects to the URL and then runs OAuth. So the button only works once `/mcp` is an OAuth-protected resource (part 3). API tokens alone cover Claude Code and the manual JSON config, not claude.ai.

Effort guess: part 1 is small, part 2 is medium, part 3 is medium. Most of part 3 comes from Better Auth's OAuth provider plugin (`@better-auth/oauth-provider@1.7.18`, same version as our `better-auth`).

## Part 2: MCP server and API tokens

### 2.1 Move automation logic out of the Server Actions

`src/lib/actions.ts` gets the user from the session cookie (`guard` → `requireUserId`). MCP requests have a bearer token, not a cookie. So:

- New `src/lib/automations/service.ts` holds the logic as plain functions that take `userId`: `create`, `save`, `goLive`, `pause`, `duplicate`, `remove`, `resetRuns`, plus `checkLive`, `parseContent`, `loadOwn`.
- `actions.ts` becomes thin wrappers: `guard(userId => service.x(userId, ...))`.
- MCP tools call the same service. Validation, conflict checks and the "one live automation per post/keyword" rule then can't drift between UI and MCP.
- Every lookup still goes through `requireAccount(userId)` / `getAutomation(account.id, id)`, so a token only ever reaches its own user's account (CLAUDE.md workspace rule).

### 2.2 API tokens

New table `api_tokens` (migration `0005_api_tokens.sql`):

| column | notes |
|---|---|
| `id` | uuid |
| `user_id` | FK `auth_user`, cascade delete |
| `name` | "Claude Code", "Cursor" |
| `prefix` | first 8 chars, shown in the UI |
| `token_hash` | SHA-256 of the token, unique. The token itself is never stored. |
| `last_used_at`, `created_at`, `revoked_at` | |
| `expires_at` | nullable. Null means the token never expires. |

- Format: `adc_` + 32 random bytes, base64url. The prefix makes leaked tokens easy to spot and to add to secret scanners.
- Shown **once** at creation, with a copy button.
- **Optional expiry** (decided 2026-11-09): the create dialog has an "Expires" select: Never (default), 30 days, 90 days, 1 year. Expired tokens are rejected like revoked ones, and the token list shows "Expires in 12 days" or "Expired".
- `src/lib/mcp/tokens.ts`: `createToken(userId, name)`, `listTokens(userId)`, `revokeToken(userId, id)`, `userForToken(raw)` (hash, look up, skip revoked or expired, update `last_used_at` at most once a minute).
- Server Actions for create/revoke in `actions.ts`.
- Local no-login mode: tokens belong to the `local` user, same as everything else.

### 2.3 The `/mcp` endpoint

- Packages: `@modelcontextprotocol/sdk` and `mcp-handler` (Vercel's adapter for Next.js route handlers, Streamable HTTP).
- Route: `src/app/mcp/route.ts` (served at `/mcp`, not `/api/mcp`, to match the URL we hand out). Export `GET`, `POST`, `DELETE`.
- **Stateless** (no session store). Fine on Vercel serverless; every request carries its token.
- Auth: wrap with `withMcpAuth(handler, verifyToken, { required: true })`. `verifyToken` accepts an `adc_` API token (part 2) or an OAuth access token (part 3) and returns `{ extra: { userId } }`. Missing or bad token → `401` with `WWW-Authenticate: Bearer resource_metadata="<appUrl>/.well-known/oauth-protected-resource"`.
- `src/proxy.ts` matcher: exclude `mcp` and `.well-known/` so the sign-in redirect never hits them.
- Base URL from `appUrl()` everywhere. Never hardcode `chat.tryadeli.com`; self-hosters get their own.
- Server `instructions` string: a short explainer of how Comment to DM works (opening DM with button, final DM with link, Meta limits from PRD §2), so Claude writes valid automations on the first try.

### 2.4 Tools

All in `src/lib/mcp/tools.ts`, each with a zod input schema (reuse `src/lib/automations/schemas.ts` and `LIMITS`), MCP annotations, and both `structuredContent` and a short text summary.

| Tool | Annotations | What it does |
|---|---|---|
| `get_workspace` | read-only | Connected Instagram account, Adeli key status, automation counts by status. Tells Claude early if setup isn't done. |
| `list_automations` | read-only | Filter by `status`. Returns id, name, status, trigger summary (`triggerSummary`), post caption/permalink, stats, updated time, and the app URL `/automations/<id>`. |
| `get_automation` | read-only | Full content + stats for one id. |
| `list_posts` | read-only | Recent Instagram posts via `listMedia` (paged): media id, caption, type, permalink, date. Needed to pick a post. |
| `create_automation` | write | Every field optional; missing ones come from `defaultAutomationContent`. `mediaId` is resolved to a `mediaSnapshot` server side. Always creates a **draft**. |
| `update_automation` | write | Partial patch merged onto the current content, then `parseContent`. If live, runs the Go Live checks first (D4). |
| `go_live` | write | Validates (`validateForLive`, `findConflict`) and goes live. |
| `pause_automation` | write, idempotent | |
| `duplicate_automation` | write | |
| `delete_automation` | destructive | |
| `reset_runs` | destructive | Clears who was messaged + stats. |

Errors: return `isError: true` with the field errors from `validateForLive` keyed by field path (e.g. `finalDm.buttons.0.url: Use an https link`) and the conflicting automation for conflicts, so Claude can fix and retry without asking the user.

Out of scope for v1: managing the Adeli key or connecting Instagram (stay in the app; `get_workspace` links there), reading individual runs.

### 2.5 Settings UI: "MCP & APIs" page

Modeled on the Twenty screenshot. Its own top-level page at `/mcp-apis`, listed in the sidebar next to Settings (changed 2026-11-09; it started as a card on the main Settings page).

- **Quick install**
  - *Claude*: "Install" button opening the preset link above. Hidden or disabled with a note until part 3 ships.
  - *Claude Code*: copyable command:
    `claude mcp add --transport http adeli-chat <appUrl>/mcp --header "Authorization: Bearer <token>"`
  - Optional later: Cursor (`cursor.com/en/install-mcp?...`) and VS Code (`vscode:mcp/install?...`) links, same builders Twenty uses.
- **Manual configuration**: the JSON block with a copy button:
  ```json
  {
    "mcpServers": {
      "adeli-chat": {
        "url": "https://chat.tryadeli.com/mcp",
        "headers": { "Authorization": "Bearer <YOUR_API_TOKEN>" }
      }
    }
  }
  ```
  After a token is created, the snippets fill in the real token (only while it's still on screen).
- **API tokens**: list (name, prefix, last used, created, expiry), "Create token" dialog with the optional expiry, "Revoke" with an alert dialog.
- Link builders in `src/lib/mcp/install-links.ts` with unit tests.
- Brand tokens and `components/ui` only; no em dashes in copy.

## Part 3: OAuth for claude.ai and Claude Desktop

- Add `@better-auth/oauth-provider` (and the `jwt` plugin it builds on) to `src/lib/auth/server.ts`. It provides:
  - `/.well-known/oauth-authorization-server` (and OpenID metadata)
  - dynamic client registration (claude.ai registers itself)
  - authorize + token endpoints with PKCE
- Add `/.well-known/oauth-protected-resource` route pointing `/mcp` at our authorization server.
- Login during OAuth is the existing Google sign-in. Add a small **consent page** ("Claude wants to manage your automations") using our brand.
- `verifyToken` in `/mcp` also accepts these access tokens (verify via the plugin / JWKS), mapping to the same `userId`.
- New Better Auth tables via its schema generator → Drizzle migration `0006_oauth.sql`.
- Local no-login mode: OAuth has no sign-in to run, so the Claude button stays hidden and API tokens are the way in. Deployed mode always has Google, so it works there.
- Settings shows connected OAuth apps (e.g. "Claude, connected 2 days ago") with "Disconnect".
- Test: run the full flow against the real claude.ai connector on a preview deployment, plus Claude Desktop.

Before building, confirm on a preview deploy that claude.ai accepts the plugin's discovery and DCR responses as is (redirect URI `https://claude.ai/api/mcp/auth_callback`).
