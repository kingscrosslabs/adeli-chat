1 · How search and AI search find you

Google

Crawlers read your pages, add the ones they trust to the index, then rank them for each search. Where you land depends on whether the page answers the search, and how much Google trusts the domain.

AI answer engines

ChatGPT, Claude and Perplexity run their own searches on engines like Google and Bing, read the top results, and cite a few pages. If search engines can't find you, the AI can't either.

What this audit checks

That your pages are quotable (A), found fast (B), never contradict each other (C), and that the setup keeps itself right on every new page (D).

Critical C2 · C3 · A6 · A1 Head and metadata

The homepage has no canonical, no share card, and a 56-character description

Evidence

The raw HTML of https://www.ledachat.com/ has 0 link rel="canonical", 0 og:* tags and 0 twitter:* tags. The same is true after JavaScript runs in a browser, and for the Googlebot, GPTBot and ClaudeBot user agents. /?utm_source=test also has no canonical, so every tagged link is a separate, unclaimed copy. The meta description is "Comment-to-DM workflow, with an MCP. Free & open source.", 56 characters against a 110–160 target. Sweep: missing_canonical 1/1, missing_og_image 1/1, description_out_of_range 1/1.

Where it lives

apps/landing-page/src/app/layout.tsx: the metadata export sets only title and description. No metadataBase, alternates.canonical, openGraph or twitter, and no opengraph-image file in src/app/. (src/lib/site-url.ts already resolves the production host, https://www.ledachat.com, from Vercel.)

The principle

A canonical tells search engines which address is the real one, so ?utm_source=… copies and shared links all credit the same URL. The og:* tags are the card people see when the link lands in Slack, iMessage or LinkedIn; with none, every share shows a bare URL. The description is your two-line ad in Google, and at 56 characters you're leaving most of it blank, so Google writes its own from whatever text it picks.

Prompt to fix it
In apps/landing-page/src/app/layout.tsx, extend the metadata export: set metadataBase to new URL(siteUrl()) from src/lib/site-url.ts (don't edit that file), alternates.canonical "/", and openGraph (type "website", url "/", siteName "LedaChat", the page title, and a description) plus twitter (card "summary_large_image"). Rewrite the description to 110–160 characters using only claims already on the page (free, open source, Instagram comment-to-DM, MCP, ManyChat alternative), and use it in og:description too. Add src/app/opengraph-image.tsx that renders a 1200×630 card with the LedaChat name, the H1 "Turn Instagram comments into DMs, for free" and the brand colors from docs/design.md. Don't touch other files. Done when yarn workspace @adeli-chat/landing-page build passes and the built homepage HTML has one absolute canonical https://www.ledachat.com (no query string, also on /?utm_source=test), og:url equal to it, og:title, og:description, og:image (1200×630) and twitter:card summary_large_image. After deploy, curl https://www.ledachat.com/?utm_source=test and check the same tags.

Critical A4 Structured data

No structured data at all, though the page already has a 7-question FAQ

Evidence

The homepage has 0 application/ld+json blocks (sweep: no_jsonld 1/1; confirmed in the browser). So there's no Organization, WebSite or SoftwareApplication telling machines what LedaChat is and who makes it. The FAQ section (#faq) shows 7 real questions in the server HTML, for example "Is this allowed by Instagram?" and "Why use LedaChat over ManyChat?", with no matching FAQPage markup.

Where it lives

apps/landing-page/src/components/landing-page.tsx (the Faq() items are inline JSX); no JSON-LD helper exists yet, so add apps/landing-page/src/components/json-ld.tsx.

The principle

JSON-LD is a label written for machines: "this is a software product, made by this company, and here are its questions and answers." Without it, Google and AI tools have to guess from the layout. FAQ markup is the cheapest version of this, because the questions are already written; it only has to match the visible text word for word.

Prompt to fix it
In apps/landing-page, add src/components/json-ld.tsx that renders one script type="application/ld+json" with an @graph of: Organization (name "King's Cross Labs" as the publisher, url, logo from /icon.png, sameAs only the GitHub repo https://github.com/kingscrosslabs/adeli-chat unless I give you other profiles), WebSite (name "LedaChat", url https://www.ledachat.com), SoftwareApplication (name LedaChat, applicationCategory "BusinessApplication", operatingSystem "Web", a free Offer with price "0", using only facts already on the page; don't invent ratings or prices for Pro), and FAQPage. In src/components/landing-page.tsx, move the Faq() items into an exported array with a plain-text answer for each, so the visible FAQ and the FAQPage markup read from the same source and can't drift. Render JsonLd once from the landing page. Only change those two files. Done when the build passes, the homepage HTML has one JSON-LD block that parses with JSON.parse, the FAQPage answers match the visible text, and https://search.google.com/test/rich-results shows FAQ and Software App as valid after deploy.

Critical B1 (partial) Crawl files

The sitemap works but carries no last-modified date

Evidence

/sitemap.xml loads, is named in robots.txt, and lists the one indexable page on the right host (https://www.ledachat.com). It has no <lastmod>, only changefreq and priority, which Google ignores.

Where it lives

apps/landing-page/src/app/sitemap.ts

The principle

The sitemap is the map you hand crawlers. lastmod is the one field on it Google actually uses: an honest date makes it re-check a page that changed. Leave it out and Google re-crawls on its own schedule; set it to "today" on every build and Google learns to ignore it.

Prompt to fix it
In apps/landing-page/src/app/sitemap.ts, add lastModified for the homepage from the last git commit that touched the page's content (src/components/ and src/app/page.tsx), read at build time with git log -1 --format=%cI. If git history isn't available (a shallow clone), leave lastModified out rather than using the build time. Drop changeFrequency and priority. Only change sitemap.ts. Done when the build passes and /sitemap.xml shows a lastmod equal to that commit's date, and it doesn't change on a rebuild with no content change.
Effort: SOwner: your agent

Important B2 Crawl files

No llms.txt

Evidence

/llms.txt, /llms-full.txt and /index.md all return 404.

Where it lives

Nothing generates it. Add apps/landing-page/src/app/llms.txt/route.ts.

The principle

llms.txt is a short plain-text summary of the site written for AI tools: what it is, in one line, and links to the pages that matter. It's an unofficial convention that not every engine reads yet, but it takes minutes, and for a product AI tools get asked about ("free ManyChat alternative") it's a clean, quotable statement of what LedaChat does.

Prompt to fix it
Add apps/landing-page/src/app/llms.txt/route.ts that serves text/plain at /llms.txt, statically generated at build. Start with "# LedaChat" and a one-line summary, then a short section built from the landing page's own copy (what it does, the free plan, the MCP, self-hosting, the FAQ answers), and links to https://www.ledachat.com, the GitHub repo and the waitlist. Read the FAQ from the shared array the Structured data package exports from src/components/landing-page.tsx if it exists; don't edit that file. Use siteUrl() from src/lib/site-url.ts for absolute links. Done when the build passes and curl https://www.ledachat.com/llms.txt returns 200 text/plain with that content.

Important C5 (partial) App host

The app's sign-in page at app.ledachat.com can be indexed

Evidence

https://app.ledachat.com/sign-in returns 200 with about 10 words, the generic title "LedaChat", and no robots meta or X-Robots-Tag. app.ledachat.com/robots.txt isn't a robots file: it 307-redirects to /sign-in. The signed-in routes (/automations, /settings) 307 to sign-in and /mcp returns 401, which is right. On www, the landing site itself is clean: /sign-in, /dashboard and unknown paths return a real 404 with noindex.

Where it lives

apps/web/src/app/layout.tsx (no robots in metadata), apps/web/src/proxy.ts (the matcher sends /robots.txt to sign-in), and no apps/web/src/app/robots.ts.

The principle

A login screen is a thin page with no answer on it. If Google indexes it, it can show up for "LedaChat" next to the real homepage and dilute it. App pages should tell crawlers to stay out, and the marketing site should be the only LedaChat page in search.

Prompt to fix it
In apps/web: set robots { index: false, follow: false } in the root metadata in src/app/layout.tsx; add src/app/robots.ts that disallows all crawling (userAgent "*", disallow "/"); and in src/proxy.ts add robots.txt to the matcher's exclusions so it isn't redirected to /sign-in. Self-hosted installs get the same defaults, which is what they want too. Only change those three files. Done when yarn workspace @adeli-chat/web test and build pass, and after deploy curl https://app.ledachat.com/robots.txt returns 200 text/plain with Disallow: / and /sign-in has meta robots noindex. If Google has already indexed it, then use Search Console's Removals tool on app.ledachat.com.

Important B5 Build hooks and guardrails

No IndexNow, so Bing and others only learn about changes when they next crawl

Evidence

Nothing in the repo mentions IndexNow, and there's no key file or deploy-time ping.

Where it lives

Add apps/landing-page/scripts/indexnow.mjs and a key file in apps/landing-page/public/; wire it in apps/landing-page/package.json.

The principle

IndexNow is a ping that tells Bing, Yandex and others "this URL changed" the moment you deploy, so they don't wait for their next crawl. Google doesn't use it, which is why B3 still matters. With one page today it's a small win, but it's set-once plumbing that pays off as soon as you add pages.

Prompt to fix it
In apps/landing-page, generate an IndexNow key, put it in public/<key>.txt, and add scripts/indexnow.mjs that POSTs every URL in the built sitemap to https://api.indexnow.org/indexnow with host www.ledachat.com, the key and keyLocation. Run it only when VERCEL_ENV is "production", never locally or on preview builds, and never fail the build if the ping fails. Because a build-time ping fires before the deploy is live, prefer running it from a GitHub Action on Vercel's deployment_status success event for production; if that's too much, run it at the end of the production build and say so. Done when the key file loads on the live site and the next production deploy logs a 200 or 202 from IndexNow.
Effort: MOwner: your agent

Add a "check:seo" script to package.json and run it after next build in the build script. Done when the build passes on the current page and fails if you delete the description from layout.tsx.

  • Readable without JavaScript. The server HTML has 932 words against 910 rendered, including every FAQ answer inside <details>.
  • Clean headings. One H1 ("Turn Instagram comments into DMs, for free") and a clear H2 outline.
  • Real 404s. Unknown paths return 404 with noindex, not a soft 404.
  • Decorative images are marked. Both images use alt="", which is right for a mockup and a logo next to its name.
  • App routes are gated. Signed-in pages 307 to sign-in and /mcp returns 401.
  • Owned code, automatic deploys. The site is Next.js in the repo, robots.txt and the sitemap are generated from code, and Vercel deploys on push (D1).
  • Tagged outbound links. Every Adeli link carries UTMs, so tryadeli.com's analytics sees what LedaChat sends.

6 · Rules for new pages

The page-level rules this site keeps missing. Bake them into the page template or the check command (finding D2) so every new page is born with them.

  1. A real description. 110–160 characters, not the title, unique per page (A1).
  2. A self-referencing canonical and matching og:url. Comes free from metadataBase plus alternates.canonical in each page's metadata (C2, C3).
  3. A share card. An opengraph-image per page or route, 1200×630, with the page's own title (A6).
  4. Structured data. At least the site-wide graph, plus FAQPage wherever FAQs show, built from the same data as the visible FAQ (A4).
  5. Listed for crawlers. Every new indexable page goes in sitemap.ts with an honest lastModified, and in llms.txt (B1, B2).
  6. Answer first. When you add guides or comparison pages, open each section with a one- or two-sentence direct answer, and add 2–4 real FAQs (A3, A7).

What needs you

Account tasks an agent can't reach. Each one is a few clicks.

CriticalB3~10 min + DNS wait

Add ledachat.com to Google Search Console and submit the sitemap

  1. Open Search Console with the Google account OpenSEO is connected to, so the agent can read the data later.
  2. Click the property menu (top left) → Add property → choose Domain, type ledachat.com, click Continue.
  3. Copy the google-site-verification=… TXT value it shows.
  4. In the DNS settings for ledachat.com (Vercel → Domains, or your registrar if DNS lives there), add a TXT record: name @, value the string you copied.
  5. Back in Search Console, click Verify. If it fails, wait 10–30 minutes and try again.
  6. Go to Indexing → Sitemaps, paste https://www.ledachat.com/sitemap.xml, click Submit.
  7. Go to URL inspection, paste https://www.ledachat.com/, click Request indexing.
  8. Done when the sitemap status says Success (usually within a day). Then connect the property in the OpenSEO dashboard so the next audit has a baseline.

Why you: it needs your Google login and a DNS record.

ImportantB4~5 min, after B3

Import the site into Bing Webmaster Tools

  1. Open Bing Webmaster Tools and sign in.
  2. Click Add site → Import from Google Search Console, sign in with the same Google account, tick ledachat.com, click Import. This brings the verification and the sitemap across.
  3. Open Sitemaps and check https://www.ledachat.com/sitemap.xml is listed; if not, click Submit sitemap and paste it.
  4. Done when the site shows as verified and the sitemap status is Success.

Why you: it needs your Microsoft and Google logins.

Decide on landing-page analytics, then set up an AI-referrer view
